### Online, parties, dedicated server, self-update

**Self-update**: `UpdateDialog.check` (main menu, exported Windows game only) compares `MainMenu.VERSION` with the latest GitHub release, downloads `Royaltim-windows.zip`, unpacks it to `user://update/files` and a batch file copies it over the game folder after the game quits, then restarts it. Keep the CI asset name and the zip's `Royaltim/` folder.
**Online** (see `tools/server/README.md`, live at 159.194.255.184): `tools/server/backend/royaltim_backend.py` (Python stdlib: SQLite accounts / profiles / rewards, matchmaking `MODES`, one game server process per match) + autoload `Online` (`network/online/Online.gd`: device key in `user://account.cfg`, `request()`; every answer's "profile" goes to `PlayerProfile.apply_remote`). While `PlayerProfile.online` the profile is the server's: no local saves, `buy` / `equip` / `register` / `choose_starters` also go to the server (`_remote`), match coins / XP are credited by the game server's report, the HUD only shows them. The backend checks prices against `catalog.json` (exported from the game by `tools/server/export_catalog.gd`, its rules mirror PlayerProfile / Mastery - keep them in step) and refuses clients of another `config/version`. PLAY = `ModeSelect` -> `CharacterSelect` (`GameManager.matchmaking`) -> `MatchmakingScreen` (queue, then connects and `NetworkLobby.client_present_ticket`) -> SpawnSelect; HOST LAN keeps the old listen server.
**Friends and parties** (backend `friends` table + in-memory `PARTIES` / `INVITES`, `PARTY_MAX` 2): main menu FRIENDS (`ui/menus/FriendsPanel.gd`: search by nickname, requests, friends with their state, INVITE / PROFILE / remove), PROFILE (`ui/menus/ProfileView.gd`: the hero they play in its wear, level, matches / coins, everything they own as `ItemRenderer` pictures) and the party bar (`ui/menus/PartyBar.gd`, invitation pop-ups) - all fed by `Online` (`poll_party` every 3 s from `MainMenu._poll_party`, `party_action`, `set_hero` from CharacterSelect -> profile "selected_hero"). Only the leader starts the search: `/queue/join` queues the whole party (each with their selected hero), the matchmaker treats it as one unit (`queue_units`), the roster carries "party" (`CtfRules._party_mate_team`: same team); a member's menu sees the party's queue state and follows into `MatchmakingScreen` (`GameManager.matchmaking_follow`: no join, only polling).
**Dedicated server** (`network/server/DedicatedServer.gd`): `MainMenu` hands over to it with `--server` (after `--`) or the `dedicated_server` feature (export presets "Linux Server (x86_64)" / "(arm64)"); `NetworkManager.start_server(port, true)` -> `GameServer.dedicated`: no host player 1, only clients play. Standalone (`--port`, `--mode`, `--min-players`): lobby after lobby in one process. Matchmade (`--match --roster --backend --key`, started by the backend): `GameServer.roster` tickets (`claim_ticket`: name and hero come from the roster), `LobbyManager.landing_deadline` / `force_start`, `/match/ready` and per-player `/match/report`, quits after the match. Anything the host did for the server must also work without a host.

### Smoothness

- Smoothness (`NetClock`): every state carries the server's msec; clients draw other heroes `NetClock.INTERP_DELAY_MS` (100) in the past between two real snapshots (`NetworkingComponent._apply_snapshots`, render time advanced by physics ticks - the wall clock bunched them), a short velocity guess past the newest. Our own hero: snapped only past `LOCAL_CORRECTION_DISTANCE`, eased back (`_check_drift`) when the server disagrees with where we were one round trip ago 3 states in a row. Measured on a hero running through 30-230 ms of jitter: frame-to-frame unevenness 0.058 -> 0.007 m, no backward steps. The server keeps each hero's last second of positions (`ServerPlayer.position_at`) and checks client-judged hits where the shooter saw the target (`rewind_msec`: half its ping + the interpolation delay); the early-shot / reload slack grows with the shooter's ping. Hold Tab in a match (`ui/hud/Scoreboard.gd`): `GameServer.scoreboard()` (name, hero, kills, ping, alive, team) once a second as "board" in the state, `ClientWorld.last_board`.

### Hit registration

- Hit registration: a "single" bullet is judged by the client WITH the gun's spread: `PlayerInputHandler._resolve_shot` rolls it (`CombatComponent.roll_shot_direction`: `current_spread` = `(1 - accuracy) * 0.15`, tighter standing still, wider moving, plus bloom from shots less than `BLOOM_HOLD` apart - automatics spray when held, bursts stay accurate), traces that bullet from the muzzle and reports `hit_entity_id` only for what it really hits, plus `shot_dir`; the local tracer fires along the same direction (`preset_shot`, used by the next `attack()` only) and the server fires a client miss along it instead of rolling again. The server checks hits in `ServerPlayer._process_client_hit`; other fire modes still report the target under the cursor and the server shoots them itself. The crosshair ring (`PlayerHUD.Crosshair`) is as wide as the bullets may stray at the cursor. The client fires by its own clock and its inputs arrive bunched (30 Hz + jitter), so a shot up to `ServerPlayer.SHOT_GRACE` early is taken and the time is owed to the next pause (`_take_early_shot`; without it ~1 in 4 pistol hits was dropped at 60 ms jitter). Every verdict, server shot, damage and ping goes to `GameServer.hit_log` (`HitLog`): on the VPS `data/logs/hits_<match>.jsonl` + one summary line per player in `hitreg.jsonl`, read by `tools/server/hitreg_report.py`. Client-judged hits set `combat.last_shot_msec` so their damage counts for the gun's mastery.
